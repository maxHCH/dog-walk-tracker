# Swift 版採 local-first，且不回拉既有資料

Swift 版的寫入一律**先寫本機（SwiftData），再經 outbox 背景推送到 Supabase**，
本機是真相來源。現行網頁版的 `startWalk()` 直接 insert Supabase，代表**沒有訊號
就按不下「開始散步」**——對一個在戶外使用的 App 是硬傷。此外 Swift 版首次啟動
**不回拉** Supabase 上既有的三個月資料。

之所以在第一版就做而非之後補，是因為**改造成本不對稱**：資料層的形狀現在決定
只多 2–3 天，等畫面都寫完再改則需要動到每一個讀寫點，屬於重寫等級的工程。

## Considered Options

- **沿用現行做法（直接讀寫 Supabase）**：否決，理由如上——離線無法開始散步，
  且日後改造成本極高。
- **雙向同步 + 衝突解決**：否決。見下方「網頁版降級」——把重複寫入的入口關掉，
  比為一個可以直接迴避的情境寫一套衝突偵測划算得多。
- **首次啟動拉回全部既有資料**：否決。M1 沒有歷史畫面，拉下來的資料沒有任何地方
  會顯示；且屆時尚不知道畫面需要什麼形狀的資料。舊資料安穩留在 Supabase，要看就
  開網頁版。下載同步留到 M2 做歷史畫面時再處理。

## Consequences

- **網頁版降級為檢視工具**：Swift 版能記錄散步的那天起，網頁版的「開始散步」
  按鈕就要**關閉**，只保留歷史、趨勢與 AI 週報。這不是隨手的 UI 調整，而是本
  決策的**衝突避免機制**——local-first 下手機的進行中散步在同步完成前對網頁版
  不可見，若兩邊都能開始散步就會產生重疊的 session。手機是唯一寫入端。
- 本機儲存選 **SwiftData**（非 GRDB／Core Data）：資料量極小，SwiftData 被詬病的
  大量資料效能與複雜 migration 都碰不到；且其教學與錯誤訊息是現行最新的，對
  「讀懂 AI 產出的 code」這個學習模式最有利。
- Supabase schema 與 RLS 完全不變，兩個 client 共用同一份資料。
